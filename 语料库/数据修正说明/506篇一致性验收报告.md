## 三、简化总览表合并单元格修正

《语料样本总览.xlsx》原来合并了行政层级（C 列）、地区名称（D 列）和上级区划（E 列）的连续单元格。直接把单篇修正写进被合并区域，可能造成**修正值被隐藏，或者其他篇继承修正值**。

验收发现涉及 4462、8763、8996、7454、10610 的合并范围存在上述问题。本轮只拆分相关合并区块、补足拆分后新区块的起始值，**不增加任何列**；相邻的 30740、11551、49956、31229 等样本重新核验后保留其正确区划。

修正后重新解析表格中的 506 条记录（按 Excel 合并单元格的实际显示语义处理），与原始元数据相比**恰好是 44 处既定变更**：

| 字段 | 变更数 |
| --- | ---: |
| `title` | 16 |
| `fyp_name` | 11 |
| `admin_level` | 5 |
| `area_name` | 5 |
| `parent_area_name` | 5 |
| `plantype_label` | 2 |
| **总计** | **44** |

提交：`2bf10a27e69a104a5723426ce6c28d67307b54c7`。

## 四、`text_len` 的口径边界（不能视为已全部消除）

此前修改过正文内容的 **33 篇**，均已经按相同口径重新计数，并**直接更新原 `text_len` 字段**；没有保留 `clean_body_chars` 等新字段。

核对 52 篇与原始 MD 不同的文件时，另发现 **17 篇并未在该轮进行正文长度修正**，仍沿用原始数据中的 `text_len`。这些原始值与“当前 MD 去首尾空白后的 Unicode 字符数”存在差异：

原始 `build.py` 构建脚本把数据库的 `row['text_len']` **直接写入** Markdown front matter，未从最终生成的 Markdown 正文重新计数，因此不能将这些差额直接判定为恢复错误。本轮没有自行对原始口径的这 17 项批量重写。若以后明确要求 **506 篇 `text_len` 一律代表当前 MD 字符数**，应先统一口径，再对全部 506 篇重算，避免只修其中一部分。

## 五、验收方法和范围说明

1. 使用 GitHub 当前 Git Tree 对比原始与干净版的 506 篇 MD，核查唯一编号、目录归属、是否缺失以及文件 blob 一致性。
2. 对 52 篇内容与原始 MD 不同的样本逐篇读取 YAML front matter，核对实际更正字段、类型编码、行政区划层级、额外字段；核实 33 篇已修改正文的 `text_len`。
3. 逐行解析现有总览表的 506 条记录，并**考虑合并单元格的显示规则**，与原始元数据和确定的 44 处修正比对。
4. 核验两份 Excel 已经写入 GitHub，且只变更 `语料库/`。
5. **未做的事情**：没有逐页比对全部政策 PDF/Word 原件；不对用户已明确排除的媒体统计口径作额外判断；不把未经指定重算的原始 `text_len` 差额宣称为已修复。
