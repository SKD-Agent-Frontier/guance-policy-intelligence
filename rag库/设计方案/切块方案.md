# 政策语料切块方案

版本：v1.0.1

确认日期：2026-10-20

更新日期：2026-10-21

项目：管策智研——政策研究与智能辅助决策智能体

状态：方案已确认；本文为设计文档，不代表切块、模型复核、人工裁决或评测已经执行。

## 一、已确认的技术路线

采用 **结构约束＋模型辅助复核＋父子块**。

执行顺序为：

> 程序先确定结构和父子块 → 大模型全量复核 → 冲突及无法判断项由人工总结、判断 → 修正并校验 → 输出正式切块结果。

本方案不采用 Docling 混合切块。大模型费用不作为限制复核范围的因素；不得将全量复核缩减为仅复核疑难样本或高风险片段。

程序负责生成初始结果和确定性校验，大模型负责全量复核并提出有原文依据的意见，人工负责争议总结与最终裁决。大模型不得直接覆盖程序结果，也不得代填人工判断。

## 二、处理范围与目标

### 2.1 输入

本阶段输入为：

`D:\桌面\“人文薪火”智能体创新应用大赛\工作区\guance-policy-intelligence\语料库\Agent标准引用库`

处理该目录中 `corpus`、`edge_cases` 下的 Markdown 文档及其引用资源信息。原始 Markdown 保持原样；解析视图、切块结果、索引增强文本和审核记录另行保存。

`project-context` 作为项目要求的背景依据。训练集用于后续问题测试与评分，不将参考答案、答案要点或模型期望回答写入政策证据索引。

### 2.2 优先级

1. 语义完整性：尽量共同保留适用对象、条件、支持方式、量化标准、例外及必要定义。
2. 章节上下文：在派生数据中保存文档标题、章节路径和来源信息。
3. 长度控制：使用所选模型对应的 tokenizer 计数，遵守实际输入硬上限。

片段必须能回到原文件。结构完整不自动等同于政策逻辑完整，模型复核通过也不等同于效果评测已经通过。

## 四、程序先确定结构和切块

### 4.1 读取文档与质量检查

- 分离 YAML 元数据和正文，沿用原有 `planid`。
- 记录源文件相对路径、文件内容哈希和处理版本。
- 检查空正文、仅标题、明显内容缺失及解析异常。
- 目录、页码等识别为辅助内容，保留原文位置，不作为独立政策事实。
- 图片引用保留资源路径和关联位置；图片中的文字是否需要识别单独评估，不假定切块已经解决图片内容缺失。

文档状态至少包括：

| 状态 | 含义 |
|---|---|
| `ready` | 可进入正常切块流程 |
| `empty_body` | 正文为空或仅空白 |
| `metadata_only` | 只有标题等信息，没有有效政策正文 |
| `needs_review` | 质量、结构或定位存在疑问 |

空正文和仅标题文档保留原文件及状态记录，不生成看似完整的政策证据。上述状态同样纳入大模型全量复核。

### 4.2 识别原文单元与层级

先建立带有原文位置的基本单元，例如标题、自然段、列表引导语、列举项、表格和图片引用。

识别依据包括 Markdown 标记、中文章节和条文编号、列表编号、段落位置、前后层级及序号连续性。程序应区分目录中的标题、正文标题及正文内对其他条款的引用。

| 原文形式 | 程序处理原则 |
|---|---|
| 第×章、第×节、第×条 | 结合位置及上下文识别对应结构 |
| 一、（一）、1.、（1）等 | 作为层级或列举线索，结合前后关系判断 |
| 无明确编号的正文 | 依据自然段、句群和内容连续线索建立初始单元 |
| PDF 转换断行 | 可以建立连续阅读视图，但保留与源文本的映射 |
| 表格 | 识别表题、表头、逻辑行、行组及合并单元格关系 |

没有明确条文的规划或政府工作报告，按原文实际章节、段落层级记录，不强行命名为法律条、款、项。无法确定的层级标记为不确定，不编造章节名称。

### 4.3 父块划分

父块是用于恢复较完整上下文的原文证据范围。程序先依据结构和关联规则确定初始父块：

| 情况 | 初始父块 |
|---|---|
| 有明确第×条 | 一条完整条文 |
| 引导语约束多个项目 | 引导语及对应的列举项目 |
| 范围明确、内容集中的小节 | 该小节或其中有共同上下文的连续部分 |
| 无编号的报告正文 | 一个自然段或具有连续关系的相邻段落 |
| 表格 | 完整表格，或有共同含义及表头约束的行组 |

不默认将整章或整篇长文件作为父块。父块本身保存原文范围，不是模型生成的摘要。

程序对前述、上述、前款、依第×条等线索记录候选依赖。相邻且应共同保留的内容可以合并；距离较远的条件、定义或例外建立跨条关联。单凭关键词不能证明依赖判断正确，交由后续全量复核检查。

### 4.4 子块划分

子块在父范围内生成，主要用于精确检索。程序优先选择完整款项、段落、句群或表格逻辑行组，并结合 token 预算装配。

- 每个子块记录对应父块编号。
- 尽量避免在适用条件、计算标准或例外说明中间截断。
- 父块较短时，可以生成一个同范围的子块，不硬性拆分。
- 不跨不同父范围机械合并子块。
- 如附加共同适用条件、标题或章节，只加入检索文本，引用仍定位到原文。

教学示例，非语料原文：

    父块 P08：完整第八条，包含适用对象和两项支持
    ├─ 子块 C08-1：完整研发补助项目
    └─ 子块 C08-2：完整设备补助项目

父子关系提供回取机制，不自动证明父块已经包含全部政策条件。跨章节依赖另行记录。

### 4.5 冻结程序版

完成初始结构、父子划分和长度校验后，保存程序版的单元、边界、关联及切分依据，再进入模型复核。

程序版作为独立版本保留。模型意见、人工裁决和最终结果应能与该版本对应，不通过覆盖丢失程序原始判断。

### 4.6 程序实现与开源复用

父子块程序采用 **定制政策结构切分器＋复用 LangChain 父子检索机制** 的实现路线。政策切分器负责依据本库原文结构确定边界，LangChain 负责对接子块检索和父块回取；开源框架的通用切分示例不直接作为政策结构判断依据。

| 部分 | 实现职责 |
|---|---|
| 定制政策结构识别 | 依据第4.2节识别中文章节、条文、自然段、列表引导语、表格及不确定结构，处理无 Markdown 标题和转换断行等情况 |
| 定制父子块划分 | 依据第4.3、4.4节组合父范围、生成子范围，记录适用条件及跨条候选依赖、父子编号和切分依据 |
| 定制确定性校验 | 检查来源版本、原文位置映射、正文覆盖、父子归属及真实 token 长度，不依靠框架自动保证原文保真或政策条件完整 |
| LangChain 检索适配 | 使用存储接口保存父块，使用向量存储接口索引子块，根据命中子块的父编号回取相应父块；存储后端及版本在实施前固定 |

开源参考为 LangChain 的 [`ParentDocumentRetriever`](https://github.com/langchain-ai/langchain/blob/master/libs/langchain/langchain_classic/retrievers/parent_document_retriever.py)。它允许接入父、子切分器并组织父子关联，但切分边界由接入的切分器决定，不自动判断中文条款、共同适用条件或跨条依赖是否完整。

本方案先离线生成父子块，再按既定流程复核和确定最终结果。后续接入索引时保留这些结果的边界、编号及原文映射，不再次调用默认切分器重切。已生成的子块可通过 [`MultiVectorRetriever`](https://github.com/langchain-ai/langchain/blob/master/libs/langchain/langchain_classic/retrievers/multi_vector.py) 适配上述父子回取机制：将关联键显式设为 `parent_id`，与本方案编号约定保持一致，父块按相同编号保存。

检索适配层同时保留命中子块及其来源范围，供引用核验；只取得父块正文不等于保留了命中证据位置。框架返回结果后仍按第十二节执行依赖回取、预算检查和引用定位。

当前仅确认上述实现路线，尚未编写或运行切块程序，也未接入 LangChain、建立向量索引或验证检索效果。开源依赖版本、接口兼容性及代表样本验证在实施时记录。

## 五、大模型全量复核

### 5.1 全量覆盖要求

所有输入文档的处理状态、文档结构、每个父块、每个子块及其关联均须有复核记录。费用不作为减少审核对象的理由。

全量是审核覆盖要求，不要求一次调用塞入整库。超过模型上下文窗口的文档按结构分批，保留文档级适用范围、相关定义和必要上下文，检查批次边界，并记录覆盖范围。

不得将调用失败、输出缺项、漏审、上下文不完整或笼统的全部通过视为完成审核。程序应核对本批应审核的对象编号与模型实际返回的记录。

### 5.2 复核输入

向模型提供：

1. 对应的原文及必要上下文，并附原文单元编号和来源版本。
2. 程序识别的章节、段落、列表、表格等结构。
3. 父块、子块的实际边界、内容和父子关系。
4. 已记录的适用条件、跨条引用和其他关联。
5. 程序的切分依据、文档状态及异常信息。

不能只给切好的子块，让模型在缺少原文上下文的情况下判断完整性。

### 5.3 复核内容

| 对象 | 复核重点 |
|---|---|
| 文档结构 | 层级是否正确，是否误识别目录，是否被断行或表格转换破坏 |
| 父块 | 是否缺少对象、条件、标准、例外或必要定义，是否混入无关内容 |
| 子块 | 是否切断完整陈述，是否遗漏关键关系，是否需要调整边界 |
| 父子关系 | 子块归属是否正确，回取父块能否补充所需上下文 |
| 跨条关联 | 是否遗漏或错误关联其他位置的适用条件和定义 |
| 异常状态 | 空正文、仅标题、内容缺失等判断是否合理 |

模型输出调整建议时，应引用已有单元编号或可核验的原文位置，说明依据。不得重新撰写政策条款，或生成来源中不存在的条件。

### 5.4 复核状态

| 状态 | 含义 | 后续处理 |
|---|---|---|
| `pass` | 模型认可程序结果 | 保留复核记录，继续检查发布条件 |
| `conflict` | 模型与程序存在不同判断 | 进入人工冲突清单 |
| `uncertain` | 模型无法确认或上下文不足 | 进入人工处理清单，必要时补充材料 |
| `incomplete` | 调用失败、输出缺项或复核未完成 | 补齐复核，不计为通过 |

模型不得直接覆盖程序版。模型认可仅表示该次复核意见，不代表事实正确性、引用质量和问答效果已经得到独立验证。

## 六、人工总结与裁决

程序将全部冲突及无法判断项整理为可阅读的清单，人工进行总结和判断。每项至少包含：

| 信息 | 内容 |
|---|---|
| 定位 | 文档、父块、子块及原文位置 |
| 原文依据 | 相关原文、前置条件及必要上下文 |
| 程序结果 | 原划分、关联和判断依据 |
| 模型意见 | 不同判断、调整建议及其原文依据 |
| 人工结论 | 保留程序结果、采用模型建议、另行调整或待补充 |
| 最终处理 | 实际修改、处理人、时间和结果版本 |

人工结论字段由人工填写。未填写或未明确裁决的项目保持待处理，不自动通过，也不由模型代填人工同意。

应用人工裁决后，重新运行原文定位、编号关联、覆盖及 token 校验，并复查受影响内容。保留模型原意见和人工裁决；不以反复调用直到模型同意代替人工判断。

新发现的争议继续进入人工清单。人工裁决不能使原文改写、错误定位或输入硬超限变成可发布结果，仍须满足确定性要求。

## 七、token 长度控制

实现时固定 embedding 模型、tokenizer 及版本，并设置真实输入硬上限。模型和 tokenizer 尚未选定时，不把中文字符数冒充模型 token 数。

首轮可将 768 token 作为可调整的目标长度，不预先认定为最优值：

- 完整单元超过目标、但没有超过模型硬上限时，优先完整保留。
- 超过硬上限时，按更细的款项、句群或表格行组划分，保留父块与必要依赖。
- 无法安全拆分的内容记录为异常，不静默截断。

计数对象为实际送入 embedding 模型的全文，包括标题、章节、附加上下文和正文，并按模型要求计算特殊 token。仅存储而不发送的元数据不计入该次输入。

回答阶段另用回答模型对应的 tokenizer 检查提示词、问题、历史及回取证据的总预算，并为输出留出空间。费用不受限不代表模型上下文窗口无限。

## 八、原文保真、表格和引用

### 8.1 原文与检索文本分离

- 原文件是引用依据，索引增强信息不写回原文。
- 解析或检索视图可以处理断行、附加标题、转换表格表示，但必须保留到原文的映射。
- 引用时按来源版本和位置从原文提取，不把模型解释或索引前缀作为政策原句。
- 重复文本结合结构及顺序定位，不能只取第一次匹配。
- 映射无法可靠建立的内容标记异常，不伪造位置。

原文范围统一采用完整原文件解码字符串中的 Unicode 码点下标，从 0 开始、右端不包含；原文件换行保留，不混用 .NET／JavaScript 的 UTF-16 下标。转换和展示环节应显式适配。跨多个范围的片段使用范围列表，每个引用范围均应可独立核验。

### 8.2 表格与资源

- 优先保留完整逻辑行和有共同含义的行组。
- 表头或表题的重复仅用于派生检索表示，引用仍对应源表。
- 合并单元格的约束范围应随相关行共同保留或建立关联。
- 无法正确解析的表格、超长单行或缺失的图片内容进入异常及审核记录。

表格和资源相关的程序结果均纳入全量模型复核；模型存在不同意见或无法判断时转人工。

## 九、主要数据约定

| 字段 | 用途 |
|---|---|
| `planid` | 原文档编号，保持与题库的对应关系 |
| `source_path`、`source_hash` | 来源位置与原文版本 |
| `title`、`section_path` | 文档标题及原文章节路径 |
| `parent_id`、`chunk_id` | 父块、子块身份及归属 |
| `source_spans`、`offset_unit` | 原文范围及下标单位 |
| `retrieval_text` | 实际用于检索或生成向量的文本 |
| `tokenizer_id`、`token_count` | token 计数依据及结果 |
| `related_ids` | 必要的跨条关联 |
| `split_reason` | 程序确定边界的依据 |
| `version`、`status` | 结果版本及处理状态 |

模型复核记录另保存对象编号、输入版本、模型及提示词版本、复核状态、意见和原文依据。冲突记录同时保存程序结果、模型意见和人工结论，保证能回溯。

以上为逻辑数据约定，实施时可采用等效结构，但不得丢失对应能力。对于来源中缺失的地区、时间或章节信息，明确标记缺失或推断来源，不擅自当作原文事实。

## 十一、验证与正式输出条件

### 11.1 程序确定性检查

- 原文范围能够还原，对应来源版本一致。
- 片段没有引用模型生成或改写的政策原句。
- 父子编号、归属及关联有效，没有串文档。
- 检查有效正文的覆盖，区分有意排除的目录、页码和真正遗漏。
- token 计数针对实际输入，无静默截断和未处理的硬超限。
- 全量审核对象均有对应记录，失败或遗漏单独统计。

### 11.2 语义与问答效果验证

先使用覆盖中文编号、无明确标题、长段落、表格、断行、跨条依赖及异常文档的代表样本验证实现，再全量处理。样本验证不替代全量模型复核。

用相同原文版本、相同问题和可比的证据 token 预算，检查证据召回、条件和例外遗漏、回答准确性及引用准确性。题库若只提供文档编号和答案要点，需核验或补充证据范围后，再计算片段级证据指标。

模型全量复核完成不自动等于问答效果达标；未运行的评测不能写为通过。

### 11.3 正式输出

每个正式发布对象须满足确定性检查，并具备完整的模型复核记录；有冲突或无法判断时，还需有明确的人工处理结论。

仍未完成审核、未获裁决或源文缺失的内容单独保留状态，不静默丢弃，也不混入已完成结果。报告区分已通过模型复核、经人工裁决完成、待处理及不生成证据的文档和片段。

人工裁决后发生的实质变更应校验并复查受影响范围。未变化且来源、内容、关联和版本一致的记录可以保留其有效审核依据。

## 十二、后续检索接口

离线切块完成后，检索以子块定位相关内容，再按 `parent_id` 和必要关联回取原文证据。回取结果需去重、检查上下文预算，并核对是否足以支持回答。

引用标注应指向实际支持结论的原文范围。对象条件和金额分别来自不同条款时分别标注，不仅挂一个金额子块而省略条件出处。

本方案当前交付范围为切块设计。向量索引构建、在线问答和正式效果评测在后续实施中分别记录完成状态。

## 十三、实施前需固定的配置

- embedding 模型、tokenizer 及版本，目标长度和硬上限。
- 执行全量复核的模型及版本、上下文预算和输出格式。
- 程序结构规则、提示词、切块及原文位置映射的版本。
- LangChain 依赖版本、检索适配方式，以及父子编号与存储接口的映射。
- 文档、父块、子块编号和结果版本规则。
- 人工冲突处理的记录方式。

以上是实施配置项，不改变已确认的核心流程：**程序先确定，大模型全量复核，冲突和无法判断项由人工总结并裁决。**
