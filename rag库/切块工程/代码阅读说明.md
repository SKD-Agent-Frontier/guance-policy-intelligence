# RAG 切块代码阅读说明

本文解释代码实际怎样运行、关键变量表示什么，以及为什么保留这些边界。代码内同步补充了中文注释。示意文字不属于真实政策证据。

## 1. 先看入口，再看一篇文档的处理

建议从 [chunk.py](chunk.py) 的 `main()` 开始，再读 [pipeline.py](policy_chunker/pipeline.py) 的 `build()` 和 `process()`，最后按调用顺序读专项模块。

```text
chunk.py / main
├─ build：构建样例或完整批次
│  └─ pipeline.build
│     ├─ 固定配置、tokenizer、代码指纹与输入清单
│     ├─ 逐篇读取，或复用经过摘要检查的缓存
│     │  └─ pipeline.process
│     │     ├─ source_quality：登记正文可用性
│     │     ├─ parse：识别基础单元与章节
│     │     ├─ make_parents：组织完整上下文
│     │     ├─ make_chunks：沿可靠边界生成子块草稿
│     │     ├─ build_relations → assemble：关联原文并检查实际长度
│     │     └─ register：登记图片资源与出现位置
│     ├─ 保存逐篇结果、快照、检查点，再汇总 JSONL
│     └─ validate_run → report：独立校验与报告
└─ validate：读取已有批次配置和 JSONL，重新校验，不重新切块
```

`build()` 解决整批执行与恢复，`process()` 解决一篇文档的内容处理。阅读具体切分规则时，先看 `process()`，不必从缓存和报告代码开始。

## 2. 原文究竟保存在哪里，位置如何计算

[source.py](policy_chunker/source.py) 的 `Source` 保存同一份输入的几个视图：

| 字段 | 含义 | 不能混淆的对象 |
|---|---|---|
| `raw` | 从磁盘读取的原始字节 | 不是清洗后的 UTF-8 文本 |
| `text` | 严格 UTF-8 解码后的完整字符串 | 包括 YAML、空格和原始换行 |
| `metadata` | front-matter 的解析字段 | 用于过滤/展示，不代替正文 |
| `body_start` | 正文在完整字符串中的起点 | 不表示删除了前面的字符 |
| `offsets` | 每行起点与文件末尾位置 | 使用码点，不是字节位置 |
| `source_hash` | 原始字节的 SHA-256 | 检查内容、换行等是否变化 |
| `version` | planid 与来源摘要决定的文档身份 | 来源变化后形成新版本 |

读取方式是 `read_bytes().decode('utf-8', errors='strict')`。如果直接默认 `read_text()`，Python 可能把 CRLF 转成 LF，已有位置就会偏移。解码错误必须暴露，不用替换字符掩盖。

所有范围使用 **完整文件的 Unicode 码点下标，0 起点、左闭右开**：

```python
text = "甲😀乙"
assert text[1:2] == "😀"
```

这个 emoji 在 Python 中占一个码点，但不是一个 UTF-8 字节，也不是一个 JavaScript UTF-16 单元。前端定位时不能直接把这里的数字当作 JavaScript 下标。

`Source.segment(start, end, role)` 生成原文段、范围和辅助行号。引用的核心约束始终是 `segment['text'] == source.text[start:end]`。相同句子出现两次，必须用各自位置区分，不能只调用一次全文 `find()`。

识别代码中的 `strip()`、去 Markdown 标记、去空白比较等，只作用于临时判断视图。输出证据仍从 `Source.text` 截取，不把判断视图写回正文。

## 3. 四层对象分别做什么

| 对象 | 核心问题 | 范围关系 |
|---|---|---|
| `units` 基础单元 | 原文每一部分是什么 | 排他覆盖全文，包含空白、目录和元数据 |
| `structures` 章节/条文 | 内容属于哪个层级 | 可以嵌套，例如章包含节、节包含条 |
| `parents` 父块 | 命中后应恢复哪些完整上下文 | 包含其成员单元与子块正文 |
| `chunks` 子块 | 哪些完整范围用于检索定位 | 不跨父块拼接，必要上下文另存 |

[structure.py](policy_chunker/structure.py) 先建立 Markdown 线索和保护范围，再按原始行扫描，最后用标题栈建立章节并分配归属。

- `protected[a] = (b, kind)` 表示原文件第 `[a,b)` 行必须整体处理，例如表格、代码块、完整 Markdown 列表项。
- `token.map` 来自只读正文的解析器，需要加 `body_line` 才能换回整文件行号；不会采用解析器重新渲染的正文。
- `headings` 暂存标题候选；`stack` 处理层级。同级或更高层级的新标题会结束前一章节。
- `active/index` 按有序位置给单元分配章节，避免逐个单元扫描全部章节。
- 文档根 `title=None`、`path=[]`，表示没有编造一个不存在的章节标题。

“带 `##`”不必然是标题。代码同时检查长度、标点和编号；“按照第八条执行”也不作为新条文。目录线索依赖目录标题、引线和页码，属于保守规则，不能保证发现所有格式的目录。

极度断行的文件会跳过 Markdown 解析器线索，继续按原文规则扫描，并登记降级状态。这不等于自动修复断行，更不表示乱码已被恢复。

## 4. 父块与子块如何生成

[chunking.py](policy_chunker/chunking.py) 的 `make_parents()` 使用 `selected` 收集当前父块的单元，`end_i` 标记已经消费到哪里：

- 条文优先完整保留；代码等字面块单独保留。
- 表题、单位、完整表体及相邻附注尽量组成表格父块。
- 冒号结尾的引导语与后续可靠列表项组成列表父块。
- 普通正文只合并同章节连续段落，3072 token 是组织参考，不是固定截断点。

`make_chunks()` 先尝试同范围短子块，再组织完整原子范围。`atoms` 是可保留的原文范围，`packed` 是准备合并成一个子块的相邻候选。

| 参数 | 实际作用 |
|---|---|
| 768 | 子块拼接目标；完整段落可以超过它 |
| 3072 | 普通父块组织参考；完整条文等可以超过它 |
| 8192 | 完整检索输入硬上限；超限不能静默截断 |

一个完整段落若超过 768、但完整输入未超过 8192，会优先保留。只有超硬上限才尝试 `sentence_ranges()`；引号/括号未闭合时不在其中截断，小数点也不作为句终。

`sentence_ranges()` 的 `cursor` 是尚未输出的起点，`depth` 是未闭合符号栈。句终后的原始空白归前一范围，保证拆分后拼接仍是原字符串。没有可靠边界就保留整段，最终标记待处理。

### 表格为什么不能简单“每十行一块”

`TableGrid` 只读取 HTML 网格结构，不转写原表。`occupied[c]` 表示第 `c` 列被占用到的排他行号。

例如第 0 行的某格 `rowspan=2`，该列记为 2；处理第 1 行时它仍被占用。必须等第 1 行结束、该行组全部跨度都结束，才允许切分。`colspan` 还需要检查是否与已有占用冲突。

`table_groups()` 同时检查列数、连续性、行组完整性和表头线索。返回的行组位置最终加上 `unit.start`，转换为完整源文件位置。共享表头、表题、单位和附注单独保存为上下文，每个检索行组都能带回。

Markdown 表格会检查表头分隔线和列数，转义竖线与行内代码只用于辅助计数。判断不可靠的超长表格进入 pending，不猜测列对应关系。

## 5. 条件、跨条引用和 token 怎样结合

[relations.py](policy_chunker/relations.py) 的 `build_relations()` 先扫描整篇已建好的条文索引，因此可以解析向前和向后引用。

`trigger` 保存触发关系的原句位置；`target_id/target_kind` 指向真正需要提供的 unit 或 parent；`rule/status` 说明怎样解析、是否唯一成功。

`legal_reference()` 会看“第×条”前后的语境，区分“按照第二条规定”和“新建第二条生产线”。显式条号优先匹配同编号作用域；仍不能唯一确定时保持 unresolved。`前款` 需要当前条文内可确认的前一自然段，不能随便拿“前一句”替代。

`assemble()` 完成最后一道装配：

1. 收集父块已登记的共同条件、定义、例外和明确引用目标。
2. 沿已保存关系带回必要依赖；`visiting` 检查当前递归路径中的环。
3. 按精确原文范围去重；正文已完整包含的上下文不重复加入。
4. 重新生成 `retrieval_text`，用真实 tokenizer 计数并求实际输入摘要。
5. 补上下文后若超限，只尝试允许的安全细分；仍超限或有未解决依赖则 pending。

这里展开的是明确登记的关系图，没有模型推理，也不保证识别全部隐含条件。

### Qwen 在本工程中的作用

[tokens.py](policy_chunker/tokens.py) 只加载分词器和官方聊天模板。`render()` 构造完整输入，`count()` 禁止截断并返回实际 token 数。

加载使用 `local_files_only=True` 与 `trust_remote_code=False`，处理时不隐式联网，也不运行远程模型代码。[prepare_model.py](prepare_model.py) 是独立准备脚本，仅下载白名单中的 7 个配置/词表文件，没有下载 8B 参数权重。

`retrieval_text` 包含程序增加的篇名、地区、章节和范围标签，是派生检索文本。真正可引用的原句来自 `source_segments/context_segments`，两者不能混用。

## 6. 如何沿 ID 找回一条证据

```text
chunks.document_id  ──→ documents.id ──→ snapshot / source_hash
chunks.parent_id    ──→ parents.id
parents.structure_id──→ structures.id ──→ path / 原文范围
parents.unit_ids    ──→ units.id
chunks.required_relation_ids ──→ relations.id
relations.target_id ──→ units.id 或 parents.id（由 target_kind 区分）
media_occurrences.asset_id ──→ media_assets.id
```

以下是只读核对单个原文段的示意；变量应取自同一批次的真实记录：

```python
snapshot_text = (run / document["snapshot"]).read_bytes().decode("utf-8")
segment = chunk["source_segments"][0]
assert segment["text"] == snapshot_text[segment["start"]:segment["end"]]
```

不要只保存 chunk 的文字丢掉 `document_id` 和位置，否则同句多次出现、政策更新或跨地区同文时就无法准确回溯。

图片有两层身份：[media.py](policy_chunker/media.py) 的 asset 根据字节登记，occurrence 根据文档及出现位置登记。同图可以共享资源记录，但不能共享或抹掉各自的政策出处。缺图、外链和越出文档目录的引用保留状态，不自动下载或补造。

## 7. 恢复与校验为什么有这么多检查

`pipeline.build()` 中的三个哈希用途不同：

| 名称 | 绑定内容 | 防止的问题 |
|---|---|---|
| `source_hash` | 一份 Markdown 原始字节 | 正文或元数据更新后仍当旧来源 |
| `config_hash` | 参数、模型 profile、代码指纹 | 不同规则/分词配置混用一批结果 |
| `job key` | 来源路径、正文摘要、媒体清单、配置 | 正文没变但图片变了仍错误复用缓存 |

`shard` 是单篇完整 JSON，`checksum` 验证它的实际字节，`checkpoint` 记录批次完成状态。分片和快照完整落盘后才写检查点；恢复时重新核对，缓存损坏重算，不完整派生快照可由本批源字节修复，error 记录会重试。

新来源版本另建批次，未变对象可以复用；`--resume` 不会强行允许不同代码或输入混入旧批次。

[validation.py](policy_chunker/validation.py) 有两层：

- `check_document()` 检查单篇的原文一致、全文单元覆盖、文档/章节/父子归属、关系目标、上下文装配和真实 token 数。
- `validate_run()` 从持久化 JSONL 流式重读，检查整批成员、资源与源文件哈希，再生成可用清单。

流式校验的 `heads` 为每类表保留一条前瞻记录，各表按文档顺序读取；末尾仍有剩余记录会报错，不能默默漏掉孤立对象。

| 状态/字段 | 应怎样理解 |
|---|---|
| unit `represented` | 已有子块或上下文表示，不等于已全部可用 |
| unit `excluded` | 不独立作为正文，但原文仍在 units/快照中，并有原因 |
| chunk `pending` | 保留原文和阻断原因，不进入可用清单 |
| parent `ready` | 父块已建立，不代表全部子块均可入索引 |
| document `partial` | 有可用范围，也有待处理范围 |
| `usable_chunks.jsonl` | 独立校验通过后实际允许使用的 ready 子块成员清单 |

校验失败时 usable 清单被清空，命令返回非零。程序能检查这里列出的确定性约束，不能证明所有政策语义都正确或现行有效。

## 8. 测试怎样证明这些规则有效

[tests/test_chunker.py](tests/test_chunker.py) 使用临时“测试政策”和小图片，不改真实语料。主要检查：

- CRLF、emoji 和重复句位置是否完整保留；小数、标题误标和目录是否正确处理。
- 列表共同条件、表头/单位/附注和跨条依赖是否真实进入检索输入。
- rowspan 不被切断，无法安全分组或超限时是否明确待处理。
- 故意改字、伪造 token 数、破坏父块范围、删除上下文时，校验器是否拒绝。
- 真实小批次恢复、损坏缓存重算、快照修复、临时失败重试及新版本旧快照保留。

## 9. 本次只增加解释，已有结果如何处理

本次仅增加代码注释、阅读说明和 README 入口，不改变函数签名、正则、阈值或执行语句。采用 Python AST 对比检查可执行语法未变，并运行已有测试。

原来的 [验收报告](验收报告.md)、[验收记录](验收记录.json) 和 `当前批次.json` 仍指向提交 `8bd20ed` 执行生成的批次，数据不重切、不覆盖。验收记录里的 `code_hash` 是当时执行版本的指纹，不能拿新增注释后的源码字节去声称仍是同一个哈希。

**当前 `code_fingerprint()` 包含注释字节。** 因此以后运行构建会自动产生新配置/批次标识；显式指定旧批次做 build 恢复，会因代码指纹不同被拒绝。本次没有为绕过这个保护而修改哈希算法或旧验收记录。

本次补充后的验证：12 个 Python 文件与修改前的 AST 完全一致，23 项现有测试通过；1475 个输入文件的清单/哈希以及 15 个既有交付文件的哈希保持一致。没有重新执行真实语料切块或覆盖原批次。
