# 给 Agent 负责人的接口适配说明

日期：2026-10-23。依据本地实际代码、已发布 SQLite/BM25S 和冻结 Markdown 核查。以用户当前选用的 `向量化与存储工程（降级版）` 为接入对象；原 PostgreSQL/Qdrant Server 工程保留，其 `document_status`、`smoke` 等运维能力不等同于 Agent 检索服务。

**结论：底层数据、检索和按对象 ID 回取已具备；真实 KnowledgeBase 适配、常驻加载、分页工具及新证据类型尚未接好。本轮提供说明与设计修订，没有修改生产接口。**

正文坐标设计及5份Hit/Passage样例已对齐proposal-v0.3；样例是已有真实数据的字段投影，生产接口仍待实施。旧导出脚本、原始RAG结果及核查报告保留原文件坐标；不能把样例对齐视为检索工程已经接入。

## 1. 目前接口是什么形式，什么时候加载，能否共享

| 问题 | 当前已实现情况 | 对接目标，尚待实现 |
|---|---|---|
| 同步、异步还是 HTTP | RAG 为同步 Python `query(project,text,limit=5,mode='hybrid',filters=None)`，返回包含来源/父块/文档/关系的嵌套 dict。底层是同步 `MetadataStore`、`VectorStore`、`LexicalStore`。没有 HTTP 路由 | 保持同步 `KnowledgeBase.search/read` 适配器，外部 Agent 工具继续异步调用 |
| 索引加载时机 | `query` 每次 `open_stores`、读当期成员、`lexical.load`，结束后 close。Qdrant 客户端在首次使用 dense 时才加载；纯 BM25 不加载 dense | 进程启动阶段固定 generation，预加载成员映射、章节目录、BM25S 和所需 dense 集合；就绪后再接收任务 |
| Agent 现在是否预加载 | `get_kb` 用 `lru_cache` 缓存 MockKB，首次请求走到执行编排时才建立；`Settings` 也只允许 mock | 启动时显式构建真实适配器并注入，不依赖首次请求触发；只增加 `get_kb` 分支还不够，配置校验也须同步修改 |
| 多请求共享 | CLI 项目锁会拒绝同时运行的独立命令。现有调用没有常驻共享运行时；不能称为并发服务 | 单进程内共用一个已加载运行时，接受多个请求并排队执行；证据登记仍每个 run 独立 |

代码入口：[RAG query](../../向量化与存储工程（降级版）/vector_store/operations.py)、[三个存储协议](../../向量化与存储工程（降级版）/vector_store/contracts.py)、[Agent KB](../../../agent/src/guance_agent/kb.py)、[Agent tools](../../../agent/src/guance_agent/tools.py)、[配置限制](../../../agent/src/guance_agent/config.py)。

### 必须处理的线程边界

Agent 当前用 `asyncio.to_thread(fn, ...)` 调用同步 KB。如果把启动线程建立的现有 `SQLiteMetadata.connection` 直接交给这些工作线程，会碰到 SQLite 默认线程约束；Qdrant Local 也持有本地连接及路径锁，不能假定任意线程/进程都可直接共享。

首轮采用最小方案：**一个库工作线程拥有 SQLite/Qdrant/BM25S 的完整生命周期**。

1. 启动时在该线程打开一个冻结发布，初始化所需索引和目录；启动成功后标记 ready。完整库此前已有约 9.76 GiB 冷加载峰值记录，部署需预留资源，不能把冷加载藏在 20 秒工具超时内。
2. 同步 `search/read` 将任务送入有界队列，等待该线程返回；多个 Agent 请求共享同一批索引，首轮库操作串行。共享不等于承诺多次 dense 计算同时执行。
3. SQLite 查询连接使用只读模式，不执行现有写库构造函数里的建表操作。服务不做 ingest、发布或索引更新；Qdrant SDK 的锁/WAL 等持久化维护不冒充“文件系统绝对零写入”。问题向量缓存如启用，与语料索引分开。
4. 保留项目锁及 Qdrant 路径锁。一个目录只由该运行时打开；不以多个 Web worker 各自加载同一 Local 目录，也不删除锁绕过限制。
5. 同一运行时固定 generation；更新通过关闭/重新加载或后续受控切换进行，不让一次请求混读两个发布。关闭前停止接收并处理退出。
6. 后端自行限制排队/执行时间；`to_thread` 的超时不能杀死已经开始的线程任务。客户端超时后不能将仍在执行的任务当作已取消或已释放库。

这是拟议生命周期，当前未做启动加载次数和并发测试。若之后独立部署 HTTP，可在这同一个运行时外增加传输层；本次无需改变存储接口或复制数据库。

## 2. 坐标、chunk_id 和 section_id 以谁为准

### 2.1 用现有 RAG 原始 ID，不再生成第二套

`Hit.chunk_id = source.id = record.source_id`，针对原生文本即 `chunk_<32位十六进制摘要>`。不能替换成 Agent 自行生成的 `1001__s00__p05`，也不能用向量 `point_id`、`representation_id` 或同内容指纹代替。

一个原子块可以因输入超长形成多个 embedding 表示，但仍只有同一个可引用 chunk_id。当前 42,516 个原生子块对应 42,551 个文本向量表示；表示 ID 的变化不应改变原块引用。

章节真源为 `parent.structure_id → structures.id`，形如 `section_<32位摘要>`。子块目前没有独立 section_id 字段，通过其原父块直接定位即可。`section_path` 原本是标题数组，显示时可用 ` / ` 连接；空数组保持空字符串，不制造“第一章”。

现有 RAG **没有** Agent 的持久化 `section_idx`。样例中的 idx 是脚本按 `(start, level, id)` 排序全部结构生成的文档内 0 起点编号，root=0；这是提案，不是原库字段。生产中应随发布冻结目录并返回真实 section_id，idx 仅是兼容便利参数，引用不能只绑定它。其唯一性范围是 `(generation_id, document_id, section_idx)`。

### 2.2 同一坐标系，分别表达完整块与本次可见范围

接受增加 `chunk_char_start/chunk_char_end`，并保留 `char_start/char_end` 表示本次返回的 content。两组数的职责不同，但**同样由 RAG 按原文提供**，Agent 不自行重算第二套坐标。

内部真源仍是冻结 MD 字节严格 UTF-8 解码后的完整字符串，包括 front-matter、BOM（若有）、CRLF 和原始空白；数据库范围和 ID 生成输入保持不变。

**对外统一为正文坐标：跳过头部元数据及正文前面的空白，正文首字符记为0。从这里往后，所有字符都保留并计数，包括空格、换行和Markdown符号。chunk_char_start/end和char_start/end使用这个原点，采用0起点、左闭右开、Unicode码点。** 契约标记`proposal-v0.3`，`offset_basis=body_first_non_whitespace`、`offset_unit=unicode_codepoint`。

`body_origin`记录正文首字符在完整文件中的绝对码点位置；从既有`body_start`开始，仅跳过开头满足Python `str.isspace()`的字符，无元数据时先跳过文件首BOM（若有）。`body_start`仍表示元数据结束位置，不能假定它等于`body_origin`。只跳过开头空白，不对正文内部执行去空白或换行归一化；正文全为空白时原点取文件末尾，按无正文处理。Markdown的`#`等首部符号也计数，不使用渲染后文本坐标。

检索适配器在启动时按文档版本计算并缓存原点，对外统一换算；无需数据库迁移、重切块或重建索引，沿用原chunk_id/section_id。Agent使用RAG返回的范围，不自行再次减原点；旧契约范围不能只改offset_basis后直接复用。前端使用`Array.from(body)`或明确的Unicode码点映射，不能直接套用UTF-16下标。

```python
# body_origin是原文件坐标；以下四个范围字段是正文坐标。
body = source_text[body_origin:]
assert content == body[char_start:char_end]
assert full_chunk == body[chunk_char_start:chunk_char_end]
assert content == source_text[body_origin + char_start:body_origin + char_end]
assert chunk_char_start <= char_start <= char_end <= chunk_char_end
```

章节范围、Passage.chunks及contexts中的原生文本范围同样转换为正文坐标；不同来源的上下文按各自文档原点换算。内部source_segments及[真实RAG结果](samples/真实RAG结果.json)保留文件绝对坐标，不直接作为新接口响应。正文原点之前的块范围不得静默截断为0；根目录对外从正文0起，其他异常范围先拒绝并查明原因。

标题前缀、元数据和共同条件属于检索增强输入，不能混进 content 后假称对应一对原文坐标。必要上下文单独用 contexts/关系列表保存各自来源和范围。

当前 42,516 个原生文本块均只有一个连续 `source_segments`。后续若出现不连续块，必须返回 `source_segments` 多范围，不能用最小起点/最大终点冒充完整块。该类块不进入只支持单范围的旧 Hit，先扩展类型。

### 2.3 ID 的生成、唯一性和重建稳定性

实际算法位于[来源模块](../../切块工程/policy_chunker/source.py)和[子块创建](../../切块工程/policy_chunker/chunking.py)：

```text
stable_id(kind, *parts)
  = kind + '_' + SHA256(JSON(parts, UTF-8, sort_keys=true, 紧凑分隔符))前32位

document_id = stable_id('doc', planid, source_hash)
parent_id   = stable_id('parent', document_id, start, end, config_hash)
chunk_id    = stable_id('chunk', document_id, parent_id, source_ranges, config_hash)
```

这是带类型前缀的 128 位摘要身份，按项目来源对象全库使用，并非仅在一个文档中唯一；数据库 objects 主键拒绝重复身份冲突。它不是数学上“绝不会碰撞”的保证。不同政策的相同文本仍分别保留来源身份。

**稳定性需要分情况回答：**

- 从同一套冻结切块产物重建向量/BM25 或切换存储后端，chunk_id 保持原值。换 embedding 模型可以改变表示 ID，不改变被复用的原始块 ID。
- 同来源、相同切块配置指纹及范围重跑，ID 可重现；脚本已重算核对当前 42,516 个 ID。
- **重新切块并非无条件稳定。** 当前 `config_hash` 包含配置、tokenizer profile 和代码原始字节指纹；仅修改切块代码注释，也可能改变 ID。不能承诺以后重新运行切块器旧 ID 永远不变。
- 因此历史引用保存 chunk_id＋document_id＋source_hash＋generation_id＋实际引用范围，继续保留旧对象/快照和所需发布目录。不得只拿 planid 去当前版猜测旧块，也不得因新索引上线自动清除历史引用来源。完整历史跨版本回看尚未验收。
- 向量工程另有 `document_version_id`（完整摘要前缀），与原切块 `doc_...` 是两个既有字段；样例同时返回，不能拿其中一个直接查询另一个表的主键。

## 3. 如何按块回看，如何解决超过 6000 字的续读

### 3.1 反查不需要全库扫描

当前[SQLiteMetadata.object](../../向量化与存储工程（降级版）/vector_store/sqlite_metadata.py)已有按 objects 主键查原始对象的方法。路径为：

```text
chunk_id → objects.id 主键 → chunk.source_segments / chunk.document_id
         → 原父块 parent_id → structure_id → 真实章节
         → documents.id → source_hash + snapshot → 原始冻结 MD
```

已用实际 `EXPLAIN QUERY PLAN` 验证为 `SEARCH objects USING INDEX ... (id=?)`。单纯在 chunks.jsonl 文本中找 ID 需要扫描；本地数据库不需要。不要把读取当前 generation 的全部 members 误当作按块回看的必要步骤。

给出的 chunk_id 必须验证对象种类和 planid 归属；不匹配即拒绝，不能忽略 planid 而返回其他文档。读取历史 chunk 时按其自身文档版本查快照，不强制它必须属于最新发布；若历史数据已缺失则明确 not_found。

### 3.2 增加 chunk_id，同时增加 offset / next_offset

建议兼容现有前三个位置参数，新增关键字参数；以下是**待实现签名**：

```python
def search(query, area, fyp, top_k) -> list[HitV03]: ...

def read(planid, section_idx, max_chars, *, chunk_id=None,
         offset=0, document_id=None, generation_id=None) -> PassageV03: ...
```

Agent `kb_read` 同步暴露 chunk_id、offset、文档/发布定位参数，max_chars 仍由服务配置控制。历史引用必须带冻结版本定位；有 chunk_id 时可从该对象取得版本，不依赖模型补造。

| 输入 | 行为 |
|---|---|
| 未指定 section_idx、chunk_id | 返回该文档版本的章节目录，content 为空；offset 必须为 0 |
| 仅 section_idx | 在选定章节内，从相对该章起点的 offset 读取；返回 section_id 和章节全范围 |
| 仅 chunk_id | 主键读取该原子块，在块内按 offset 读取；返回完整块范围及所属章节，不从章节开头重读 |
| 同时指定两者 | 验证属于相同冻结目录/章节；不一致返回 invalid_argument，不静默忽略 |
| offset 非整数、负数或超出所选范围 | invalid_argument；对非空范围不返回含糊的空成功页 |

**6000 字是每次可见文本的预算，不是丢弃其余原文的依据。** 常规块能放下时返回完整块，`truncated=false`；超过上限返回 `truncated=true`、`next_offset` 和实际可见范围，下一次显式续读。offset/next_offset仍为相对所选块或章节的码点数，不再次减body_origin；输出char_start/end、section_char_start/end及页内块范围统一为正文坐标。不要在响应content中插入省略号或清洗换行。

当前有 41 个原生块超过 6000 码点，最长 91,631；它们已完整保存，部分 embedding 输入另行分片。仅增加 chunk_id 不能承诺一个工具响应装下任意完整块。本地程序层应提供按 chunk_id 完整读取的 `get_chunk_source(chunk_id)` 能力，供原文界面/确定性校验使用；该完整对象不得无条件全部塞给模型。该便捷方法尚未实现，现有 SQL 对象回取已可取得完整 source_segments。

本轮分页样例取一个 6134 字块：第一页 6000 字，第二页 134 字，已断言两页相接且拼接逐字等于原块。它证明数据与拟议范围计算可行，不代表生产 kb_read 已支持分页。

### 3.3 一个块会跨章节吗

当前全量核查：原生文本块均在原父块 `structure_id` 对应的范围内，且没有块内部开启另一个已识别章节，跨章节计数为 0。`section_path` 用原父块保存的原路径，不用检索摘要推断。

额外共同条件和跨条关系可能来自别处，应在 contexts/relations 中分别给出处；不能改变主块 section_path 后把多处内容冒充一章。两个已知断词块有补充 parent_context，其作用是恢复上下文，主块归属仍沿用原父块；两种父 ID 都应保留。

此结论只针对当前被程序识别的章节结构，不等于人工确认所有标题都识别正确。图片/视觉块的章节要经 occurrence.structure_id 回取；不能直接把视觉 payload 的空路径当作“没有章节”。

## 4. Agent 如何用检索结果、如何证明出处

1. search 返回原子块 ID、完整块范围、实际可见范围、来源版本和摘要；snippet 只是定位入口。必要时按 chunk_id 读取原句及共同条件。首次命中不能自动视为完整政策证据。
2. 证据登记保存offset_basis/body_origin和两个范围：完整块范围用于回看，已提供模型的范围用于引用。多页/多次读取按chunk_id和版本合并observed_ranges，不能像当前`_refs[chunk_id]=ref`一样覆盖前一次范围；旧记录按原契约解释，不把文件坐标误作正文坐标。
3. 模型只引用 RAG 返回的 chunk_id。当前 run 的证据 ID 登记与历史会话保存分开；旧会话提到的 ID 如需作为本次证据，应重新读取并登记。
4. 引句须出自已提供的范围；按offset_basis/body_origin换回文件范围，再按source_hash/快照逐字核对。不能因为chunk存在就批准引用从未读到的后半段。当前output主要验证ID已登记，**尚未逐字验证Claim.quotes或结论支持关系**。
5. 原文入口由程序依据 generation/document_id/snapshot/范围生成；目前是本地相对快照路径，没有可供远端浏览器打开的原文 HTTP URL。接入 UI 时另做受控原文服务，不能把本机绝对路径当成已部署网址。无真实页码或官方链接时不生成这些字段。
6. 图片/OCR 保持独立类型：MD 图像链接范围不是图中文字范围；OCR 为转录码点，bbox 为图像区域且保留 coordinate_basis/原尺寸/识别版本/不确定标识。不得硬填 MD chunk_char_start/end 或混入旧纯文本 Hit。当前适配首轮应显式限定原生 text_chunk，图片分支扩展类型后再开放，不能把未适配解释为库里没有图片数据。

## 5. 当前契约样例与内部坐标对照

[Hit.json](samples/Hit.json)与[Passage.json](samples/Passage.json)来自 planid=`20699`《苏州市“十四五”民政事业发展规划》，源文件 `corpus/20699/20699.md`。实际 BM25 查询“养老服务”第 1 名：

| 字段 | 内部文件坐标：保留不变 | 当前JSON样例：正文坐标，proposal-v0.3 |
|---|---|---|
| chunk_id | `chunk_c5481643e7c67d653e29160c30719104` | 沿用原ID |
| body_start / body_origin | body_start=253，原库没有body_origin字段 | 样例增加body_origin=254，跳过元数据后的1个开头空白码点 |
| 完整块 | `[11118,11569)`，451码点 | `[10864,11315)`，仍为451码点 |
| Hit.content | `[11118,11418)`，300码点，truncated=true | `[10864,11164)`，文本及截断状态不变 |
| Passage.content | 同一块完整451码点，truncated=false | 文本不变，仅换算范围 |
| 章节 | 第四部分主要任务，`[8540,19862)` | `[8286,19608)`，章节身份不变 |
| section_id | `section_aa3464a90b5898f38ba5c38fa030ce26` | 沿用原ID |
| 拟议section_idx | 4，按此前目录投影生成，尚未持久化发布 | 编号不因原点平移改变 |
