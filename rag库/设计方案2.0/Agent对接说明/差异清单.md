RAG侧现已在[独立检索工程](../../检索工程/README.md)完成：同步search/read、独立V0.3类型、两路前置筛选、source先归一的RRF、正文坐标、冻结目录、按块/章节分页、原文主键回取、上下文/质量提示、有界队列及同线程生命周期、业务错误和按已见范围核对原句。真实完整库BM25/混合检索、共享加载及长块重建已通过[验收](../../检索工程/验收报告.md)。旧建库query保持原实现，新接入使用RagKnowledgeBase。

## 1. 双方各自负责什么

- RAG侧：上述适配、过滤、定位、坐标、目录、分页、启动与共享已实现，入口为RagKnowledgeBase。
- Agent侧：扩展Protocol、数据类型、工具入参和参数透传，接入真实后端配置，登记完整范围与已见范围，核对引用原句。
- 双方共同：使用proposal-v0.3样例作为契约依据，约定错误状态和版本定位，联调后再报告生产接入完成。

## 3. 为什么不能只增加几个JSON字段

[现有类型](../../../agent/src/guance_agent/schemas.py)会忽略未声明字段。即使底层返回chunk_char_start/end、section_id、body_origin、next_offset，旧Hit/Passage/EvidenceRef仍会丢掉它们；ToolResult数据类型和context登记也要联动修改。现行[kb_contract.md](../../../agent/contracts/kb_contract.md)中“仅加get_kb分支即可接入”的说法，不足以覆盖本次接入范围。

`_call`当前在后端执行前只验证旧参数。新参数校验、异常映射和参数透传必须一并设计，否则会把调用错误当成后端故障，或让新增参数根本传不到read。

## 4. 现有证据与样例能证明什么

- [Hit](samples/Hit.json)和[Passage](samples/Passage.json)来自同一真实块，带完整元数据、原始ID、版本和正文坐标；完整块451码点，预览300码点。
- [章节Passage](samples/章节Passage.json)包含6000码点的章节正文、10个块交集及截断状态；[长块两页](samples/长块第1页.json)与[续页](samples/长块第2页.json)覆盖同一6134码点块。
- 新样例标记proposal-v0.3，正文原点为254或253；文本、ID不变，按冻结快照逐字可还原。
- [历史核查报告](核查结果.json)记录原始范围/ID、原文哈希、主键查询计划及旧样例验证；它保持文件坐标，不是生产接口验收报告。
- 2026-10-24已新增真实RAG适配器运行、启动/并发及混合检索证据，见工程验收。Agent接入与真实模型问答准确率尚未验收。

## 5. 后续最小验收项

| 验收行为 | 应观察到的结果 |
|---|---|
| 启动后连续查询及多请求进入 | 索引只加载一次，同一运行时共享，run结果和证据不串用 |
| 以Hit中的chunk_id回读 | 对应planid、同版本原文、相同完整块范围及真实章节 |
| 对6134码点块读取offset=0、6000 | 返回6000＋134码点，页边界相接，拼接与完整原文一致 |
| 章节分页包含半个块 | 该块complete=false，只登记实际提供的交集 |
| 坐标含开头空白、内部空白、CRLF和非BMP字符 | 对外正文范围及反算文件范围逐字一致，正文内部不清洗 |
| 错误planid、未知chunk、负offset、版本冲突 | 分别按契约拒绝，不返回错误来源或空成功 |
| 多次读取同一块 | 已见范围合并，未读部分的引句不获批准 |
| 使用旧引用或重建索引 | 旧来源保留并按原版本回看；复用冻结切块产物时不重编号 |

RAG相关行为已通过工程验收；Agent运行内证据、引用展示及端到端问答仍需同事联调。本轮不改Agent、不迁移数据库、不推送或部署。
